PROJECT 01

CUDA Mandelbrot Renderer

374 ms → 1.0 ms with Nsight-validated ~370x speedup

I built a CUDA Mandelbrot renderer to study how far a compact kernel could be pushed when the launch configuration, memory access pattern, and iteration logic were tuned together instead of treated separately.

I profiled the hot path with Nsight, traced most of the time loss to unnecessary work in the iteration loop, and tightened the execution path so the GPU spent its time on actual fractal computation.

The result is a deliberately measured GPU program: easy to benchmark, easy to compare, and grounded in visible performance data instead of guesswork.

  • Reworked the kernel to reduce wasted iterations and make thread work more consistent across the image.
  • Used Nsight to validate changes and confirm the speedup was coming from real kernel improvements.
  • Kept the rendering path compact so the benchmark stays stable and easy to reason about.

PROJECT 02

Systems Grid Diagnostics

812 ms → 96 ms after flattening state updates and tightening the data pipeline

I built this as a systems-style interface for inspecting data flow, runtime status, and the parts of a UI that usually turn fragile when the state graph gets bigger than expected.

The main work was turning a noisy update path into something that stayed readable under load: I normalized state boundaries, reduced redundant rerenders, and made the data path easier to inspect while debugging.

That approach made the interface feel less like a decorative dashboard and more like a practical analysis surface for reliability work.

  • Restructured the update flow so the UI could stay responsive while still reflecting live system changes.
  • Reduced complexity in the render path by separating derived state from primary input data.
  • Made failure points easier to trace by keeping the interface aligned with actual runtime behavior.

PROJECT 03

Performance Lab

1.8 s → 140 ms after profiling bottlenecks and removing the heaviest repeated work

I treated this project like a small performance lab: measure first, isolate the slow path, then change only the parts that clearly moved the bottleneck.

That meant profiling the critical path, identifying repeated work that could be cached or batched, and simplifying the interface around the actual runtime cost instead of assumptions.

The end result is a tool that makes throughput and reliability easier to see, which is useful when I want to reason about a system instead of just watch it animate.

  • Profiled the slow path before changing behavior so the optimization work stayed grounded in evidence.
  • Reduced repeated computation and adjusted state flow to avoid unnecessary blocking work.
  • Kept the UI focused on measurable outcomes such as latency, load, and consistency.
